# Writing a Fleet Adapter

A Fleet Adapter translates between the Swarmada control plane and a robot's own
interface, so the orchestrator can command and observe robots it did not write the
software for. This guide is the copyable path from empty repo to a registered,
conformant adapter. It names no vendor and endorses no product — it describes the
process, and the [conformance suite](../adapters/CONFORMANCE.md) is the only judge of
whether an adapter is correct.

## Where an adapter lives

Per [ADR-0005](adr/0005-reference-adapter-policy.md):

- **In-tree** (`adapters/<name>/`) is reserved for project test infrastructure — the
  reference skeleton/template and the simulation adapter.
- **Every functional adapter lives in its own repository** — reference adapters for
  open, vendor-neutral interfaces and vendor-specific adapters alike — and is listed
  in the [adapter registry](../adapters/REGISTRY.md) by a single row.

You own your repository from the first commit. The project does not host, gate, or
certify it; it publishes a template and a test suite, and you self-attest.

## The path

1. **Scaffold from the template.** Generate your adapter from
   [`adapters/template/`](../adapters/template/) (cookiecutter). It emits an adapter
   already wired to the shared `swarmada-sdk` safety primitives — confirmed e-stop,
   fencing-token ordering, assignment-lease self-stop — and it redials a dropped
   stream with bounded backoff. It declares the contract version this repository
   implements, and `make spec-contract` keeps it there
   ([Contract versions and re-qualification](adapters.md#contract-versions-and-re-qualification)).
   Run unmodified with its simulated binding, it fails no conformance
   check, but its profiled verdict is `not-established`, not a pass: four required
   rows are not measured — three the harness measures for no adapter, and one that
   needs a motion witness the simulated binding cannot provide. The template's
   [README](../adapters/template/README.md#what-the-harness-reports-for-a-generated-adapter)
   lists them. Start here rather than from scratch; the safety wiring is the part you
   least want to hand-roll.
2. **Implement the contract for your interface.** Fill in telemetry (map your robot's
   position / battery / health onto the protocol's numeric fields), task execution
   (turn a `FleetAction` delivered by `assign_action` into your robot's native command
   and echo the fencing token in status; a `FleetTask` never crosses the adapter
   boundary, only its actions do), and the confirmed-stop path (report `is_stopped` only from real robot
   state, never inferred). Decline anything optional you don't support with
   `unsupported = true`.
3. **Prove it with the conformance suite.** Run the neutral
   [conformance harness](../adapters/CONFORMANCE.md) against your adapter (a simulated
   binding is enough — no hardware required) until it passes the current suite. The
   harness stamps the **contract version** your result was earned against into its
   report.
4. **Register it.** Open a pull request adding one row to the
   [adapter registry](../adapters/REGISTRY.md) with your repository, maintainer, the
   contract version, and the conformance result. The pull request *is* the
   attestation ([ADR-0007](adr/0007-conformance-self-certification.md)) — no authority
   signs off on it.

## Python and runtime versions

An adapter written in Python needs **Python 3.10 or newer** — the interpreter ROS 2
Humble, the current ROS 2 LTS, ships. `swarmada-sdk` and the adapter template declare
that floor.

The `fleet_adapter.v1` Python stubs (`proto/fleet_adapter/v1/*_pb2*.py`) import on
**protobuf 3.20.3 or newer** and **grpcio 1.64.1 or newer**. They are generated by a pinned `grpcio-tools`
(`pyproject.toml`, the `codegen` extra), because the generator decides that floor: a
newer one would raise it for every adapter.

A robot image that already carries protobuf and grpcio at or above the floor needs
nothing installed. One that carries neither — a stock ROS 2 Humble image has no
Python protobuf or grpcio — or carries an older one, needs its own copy, installed
**beside** the image's packages rather than over them:

```bash
# Either a virtual environment that can still see ROS 2's packages:
python3 -m venv --system-site-packages ~/adapter-env
~/adapter-env/bin/pip install path/to/swarmada/sdk/python path/to/your-adapter

# Or a target directory, APPENDED to the path ROS 2 set up:
source /opt/ros/humble/setup.bash
pip install --target ~/adapter-libs path/to/swarmada/sdk/python path/to/your-adapter
export PYTHONPATH="$HOME/adapter-libs:path/to/swarmada/proto:$PYTHONPATH"
```

Append to `PYTHONPATH`; never assign it. On a ROS 2 system `rclpy` and the message
packages are reached *through* `PYTHONPATH`, which `setup.bash` fills in, so
`PYTHONPATH=~/adapter-libs python3 …` removes ROS 2 from the interpreter and
`import rclpy` fails on a robot whose graph is healthy.

## What the project maintains, and what you do

The project maintains the contract, the template, and the conformance suite. You
maintain your adapter and re-run the suite when the result stops holding: on a
**major** contract-version bump; when the contract version your report carries is
outside the window the control plane accepts (minor N and N-1 of the control plane's own
contract version, within its major: `>=1.3.0 <1.5.0` at contract `1.4.0`;
the window moves only with the control plane's version, and nothing in it dates or
expires; a change that binds adapters for safety raises its floor to that version); and on each `harness`-class suite revision,
after which [`adapters/REGISTRY.md`](../adapters/REGISTRY.md) marks your row stale.
The split between what the project maintains and what you maintain is deliberate: it
keeps the standard neutral and lets the adapter ecosystem grow without any single party
in the loop. What a control plane gates admission and dispatch on is the report your
`FleetAdapter` references, not the registry row
([Contract versions and re-qualification](adapters.md#contract-versions-and-re-qualification)).
